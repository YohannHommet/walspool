How walspool Eliminates Failure Cascades

A strict boundary separates high-throughput application requests from external network variance.

01

Inbound Enqueue

Application threads call spool.Enqueue(). Preconditions are validated and an atomic monotonic ID is assigned.

⚡ 1.5 µs non-blocking
02

Binary Append + CRC32

Record is encoded with a 29-byte binary header and IEEE CRC32 checksum, then synced directly to active.wal.

🔒 Fsync durability guaranteed
03

Batch Dispatcher

Background worker drains uncommitted records in batches (e.g. 50 items). Translates transport faults into exponential backoff.

⏱️ Window or size triggered
04

Atomic Checkpoint

Upon successful sink acknowledgment, the high-water mark advances via atomic rename (.tmp → .meta).

✨ Zero log rewriting

Technical Questions

Frequently Asked Questions

Deep technical answers on durability guarantees, disk ergonomics, and operational trade-offs.

How does walspool differ from a PostgreSQL or MySQL Transactional Outbox table?

Database outbox tables introduce write amplification, table bloat (dead tuples in PostgreSQL), lock contention on high-throughput workloads, and require continuous polling workers or heavy CDC (Change Data Capture / Debezium) that increase primary database CPU.

walspool writes raw append-only binary chunks directly to local NVMe/SSD storage in 1.5 microseconds. It requires zero database connections, zero table migrations, and adds zero overhead to your relational database.

What happens if the operating system crashes or the process is killed with SIGKILL?

Every record is written with an IEEE CRC32 checksum before the Enqueue() call completes. On boot, walspool reads the atomic checkpoint.meta file, seeks directly to the last acknowledged byte in active.wal, and replays uncommitted records with zero loss. If a write was torn mid-flight by an abrupt power cutoff, the CRC32 parser detects it and isolates the corrupted tail.

Does walspool require CGO or any external binary dependencies?

No. walspool is 100% pure standard library Go (os, sync, hash/crc32, encoding/binary). It builds with CGO_ENABLED=0 into a single, statically linked binary. It runs natively on Linux, macOS, Windows, and embedded ARM architectures with zero shared library dependencies.

What delivery semantics does walspool guarantee?

At-least-once delivery. If the network drops after the remote sink receives a batch but before it returns an HTTP 200 acknowledgment, the dispatcher retries the batch upon reconnection. Downstream sinks should be idempotent. Every record in walspool includes an atomic, monotonic ID and timestamp that can be used directly as an idempotency key.

How does walspool integrate with Kubernetes and containerized deployments?

Simply mount a Kubernetes PersistentVolumeClaim (PVC) or local node NVMe path to the spool directory (e.g. /var/data/spool). When a pod is rescheduled or replaced during a rolling update, the new container mounts the exact same volume and immediately resumes draining the uncommitted backlog.

How are poisoned payloads or 400 Bad Request responses handled?

If a downstream sink permanently rejects a payload (e.g. client validation error or schema mismatch), your adapter returns walspool.ErrPermanentRejection. The dispatcher immediately advances the checkpoint past the poisonous record and flags it, preventing a single malformed event from blocking the entire pipeline.

What happens when disk storage or maximum capacity is reached?

You configure your backpressure policy. Under the default RejectOnFull setting, Enqueue() returns ErrSpoolFull immediately so your web framework can return an HTTP 503 or trigger upstream backpressure. You can also configure buffer limits up to millions of records depending on disk quota.
